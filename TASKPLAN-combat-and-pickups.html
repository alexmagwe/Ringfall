TASKPLAN — Combat, pickups & hunter abilities

A scarce-ammo retaliation loop bolted onto the stealth game, without breaking the stealth.

Context

Ringfall is pure evasion today — hunters can't be killed. This adds a costly way to fight back: scavenged pickups (gun, compass, stamina, ammo), a gun that kills a hunter in 10 hits with a draining health bar and an explosion, and a hunter summon ability so shooting has consequences.

Round 1: find compass + gun + 12 ammo, escape RUN IT BACK → new maze, empty inventory, pickups at NEW cells Round 2: find stamina-up + 6 ammo, no gun this time Two settled decisions drive everything: • PER-RUN scavenge → state lives in player attributes, wiped on restart. No PlayerData. • SCARCE gun → ammo found, never regenerates. A kill ≈ 10 rounds. Hiding stays primary.

The clean seam: hunters already have a Humanoid

The gun damages Humanoid.Health via TakeDamage; Hunter reacts to its own Humanoid.Died. So the Gun feature never touches Hunter's source — damage flows through a Roblox-native contract. The health bar just reads replicated Humanoid.Health.

Reused infrastructure — do not reinvent

ThingReuse for
workspace.MazeGeneration signalRe-scatter pickups + clear alerts each round. Initial call in Start() after MazeReady, then connect the signal — first-gen fires before listeners exist.
catchPlayer(...) closure in HunterServiceThe explosion catch — reuse in-file, don't export. No new player-HP system.
workspace.EvacAlert timestamp idiomThe summon: broadcast an event to all independent hunter loops with no signal bus.

SprintController / Controls raw HUDsAmmo counter, crosshair, compass, toast — raw instances, no React, no .ui.luau, no check-views surface.

Out of scope / Do NOT

  • No PlayerData for any pickup/ammo/upgrade — per-run attributes only. Best-time persistence is already done, untouched.
  • No player health model. "Caught" stays a checkpoint teleport; the explosion reuses catchPlayer, deals no HP.
  • No client-authoritative hits. Client sends a camera ray; the server re-raycasts from the character and applies damage. Never trust a client hit.
  • Dead hunters respawn at farSpawn after a delay. HUNTER_COUNT stays 3; the maze never empties.
  • Pickups live in workspace.Pickups, never under workspace.Maze (ClearAllChildren would eat them at an uncontrolled time).
  • No hardcoded siren. SIREN_SOUND_ID = "" seam; summon works silently until the user supplies it.
  • Reach hunters generically (Name == "Hunter"), the existing idiom — no dependency on HunterService's source.

Phase 1
Pickups — gun grant, ammo, compass, stamina

New src/features/Pickups/. Scatters world pickups at random maze cells each round; touching one grants a per-run attribute.

The per-run attribute contract

AttributeTypeMeaning
HasGunboolowns the gun this run
Ammonumberrounds left (server-authoritative)
HasCompassboolcompass HUD active
StaminaBonusnumberadded to max stamina, 0 default

1.1 Constants.luau — folder name, float height, spin, the SPAWNS table (Gun×1, Ammo×4, Compass×1, Stamina×1), GUN_START_AMMO = 12.

1.2 PickupsService.server.luau scatter() clears the folder, snapshots MazeNav.cellPos keys (excluding band 0 = the exit), shuffles with an unseeded Random so locations differ every play, and pops distinct cells per kind. Each pickup = neon ball + PointLight + PickupKind/PickupAmount attributes. Touched → grant() → Destroy() (parent-nil check debounces the multi-part double-fire).

1.3 Clear HasGun/Ammo/HasCompass/StaminaBonus in EscapeService's Restart loop — not in resetState, or a caught player loses their loot mid-run.

1.4 PickupsController.client.luau spins the balls; a raw toast flashes "PICKED UP: …" on attribute change.

1.5 SprintController reads StaminaBonus into a live maxStamina (clamp, regen, fill ratio).

1.6 CompassController.client.luau — arrow pinned top-centre, points to world-centre (the exit), only while HasCompass.

Check: balls at random cells; grabbing Gun sets HasGun/Ammo, compass shows, stamina rises. RUN IT BACK re-scatters to new cells and clears all four.

Phase 2
Hunter combat — health, death, explosion, summon

All in HunterService.server.luau. The hunter owns everything about being a hunter — no new feature.

2.1 MaxHealth = HUNTER_HITS (10); a BillboardGui over the head with a red fill, hidden until damaged. HealthChanged updates it — GUI changes replicate, so the drain is visible with zero client code.

2.2 Humanoid.Died → explodeAt(pos) (code-built neon flash, no asset), catch every player within BLAST_RADIUS = 14 via catchPlayer, destroy, then task.delay(RESPAWN_DELAY, spawnHunter) to keep the maze populated.

Why the explosion catch is safe to chain

catchPlayer early-returns on an already-Caught player, so a multi-hunter chain can't double-catch. spawnHunter is already the function the startup loop calls — re-entry is fine.

2.3 Summon consumer branch (after EvacAlert, before CHASE): reads HunterAlert (timestamp) + HunterAlertPos (a Vector3 attribute — workspace attributes accept Vector3 directly), and if recent, within SUMMON_WINDOW = 5, and this hunter is within SUMMON_RADIUS = 200, beelines to the alert. Cleared on rebuild. SIREN_SOUND_ID = "" seam. Phase 3's damage handler sets these attributes — Phase 2 only consumes.

Check: command-bar hum:TakeDamage(1) ×5 shows the draining bar; Health = 0 explodes, catches a nearby player, and a replacement appears far away ~4s later.

Phase 3
The gun — aim, fire, HUD, server-validated hit

New src/features/Gun/. Client fires; server decides.

3.1 Net.luau — namespace Gun, one Shoot packet carrying origin + direction (fall back to three float32s if ByteNet.vector3 isn't exported).

3.2 GunService.server.luau — Shoot.listen: reject unless HasGun and Ammo > 0; decrement ammo; re-raycast from the character (not the client origin) over GUN_RANGE; if it hits a Hunter model, Humanoid:TakeDamage(1); fire the summon (HunterAlert/HunterAlertPos = shooter pos). Server-side FIRE_COOLDOWN throttle per player so a spoofed client can't machine-gun.

Authority lives entirely on the server

Ammo, range, fire-rate, and whether a hunter was actually in the ray are all decided in GunService. The client packet is a request. The client's own cooldown and ammo display are feel only.

3.3 GunController.client.luau — only while HasGun: centre crosshair + "AMMO n" counter (updated on the Ammo attribute); MouseButton1 → Shoot.send({origin, direction}). Optional tracer.

3.4 Controls.luau — register "MOUSE 1 → Shoot (when armed)", order 25.

Check: no gun → clicking does nothing, no HUD. After the Gun pickup → crosshair + ammo appear; clicking a hunter drains its bar; 10 hits kills it; ammo hits 0 and clicking stops; nearby hunters converge after a hit.

Studio assets the user provides

  • Siren sound → SIREN_SOUND_ID. Summon works silently until then.
  • (Optional) explosion sound → BLAST_SOUND_ID.
  • Nothing else — pickups, crosshair, health bar, compass, explosion are all code-built.

Definition of Done

  1. split / check-views / check-framework-boundary pass after every phase.
  2. Pickups scatter at cells that differ every round, are one-grab, and all four attributes clear on RUN IT BACK (≥3 rounds).
  3. Stamina upgrade raises the bar mid-run; compass arrow tracks the centre.
  4. The gun is server-authoritative: ammo, range, fire-rate, hit validation all server-side; no fire without HasGun, past 0 ammo, or faster than FIRE_COOLDOWN.
  5. A hunter shows a draining bar, dies on hit 10, explodes, catches within BLAST_RADIUS via the checkpoint flow, and is replaced far away after RESPAWN_DELAY. Count stays stable.
  6. Shooting a hunter converges others within SUMMON_RADIUS for SUMMON_WINDOW; the alert clears on rebuild.
  7. The Gun feature never requires HunterService's source — damage only via Humanoid:TakeDamage.
  8. No PlayerData writes for any pickup/ammo/upgrade state.
  9. SIREN_SOUND_ID / BLAST_SOUND_ID are "" seams.
  10. No debug prints remain.
